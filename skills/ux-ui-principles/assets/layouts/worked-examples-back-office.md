# ตัวอย่างงานจริง: ระบบหลังบ้านการชำระเงิน (PayOps)

ตัวอย่าง 4 หน้าของระบบเดียวกัน แสดงการใช้ framework, rigor tier และ
[page spec](../page-spec.md) กับหน้าคนละประเภท ข้อมูลทั้งหมดเป็นข้อมูลสมมติ
หน้าเหล่านี้เคยสร้างเป็นต้นแบบ HTML และผ่าน render check อัตโนมัติ
(flow หลัก, จอ 1440/390, โหมดมืด) แต่ยังไม่ได้ทดสอบกับผู้ใช้จริง, screen reader หรือ API จริง

ทั้ง 4 หน้าใช้ design context เดียวกัน: role (Operator, Manager, Auditor),
ชื่อ status ("รอตรวจ", "อนุมัติแล้ว", "ปฏิเสธ", "รอ Manager"), tokens และ sidebar ชุดเดียว
นี่คือความสอดคล้องระดับระบบ แต่ layout ของแต่ละหน้าเปลี่ยนตามงาน

## 1. ภาพรวม — Overview dashboard (D01) · Standard

**งานหลัก:** Operator ต้องรู้ว่าต้องจัดการอะไรก่อน; Manager ต้องรู้ว่ายังอยู่ในเป้าไหม

**การตัดสินใจสำคัญ**
- ข้อมูลชุดเดียว แต่ลำดับตาม role: Operator เห็น "ต้องจัดการ" ก่อน,
  Manager เห็น KPI และแนวโน้มก่อน ([back-office.md](../../references/back-office.md))
- ทุก KPI มีค่าเทียบ (เป้า, เมื่อวาน) และเวลาอัปเดต; ตัวที่ผิดปกติมีแถบสีและข้อความ
- กราฟมีเส้นเป้า 99%, แรเงาช่วงผู้ให้บริการมีปัญหา, เน้นค่าล่าสุด
  ([data-visualization.md](../../references/data-visualization.md))
- รายการ "ต้องจัดการ" แต่ละข้อมีลิงก์ไปงานต่อทันที

```text
Page header: ชื่อหน้า · วันที่ · อัปเดต 14:44 · [Operator|Manager]
KPI strip (4): Success rate vs เป้า | รอตรวจ (เกิน SLA, รอ Manager) | ล้มเหลว 24 ชม. | ยอดวันนี้ vs เมื่อวาน
ต้องจัดการ (เรียงตามความรุนแรง) | Success rate รายชั่วโมง + เป้า
                                 | สถานะผู้ให้บริการ (ตาราง)
```

**Metric:** เวลาที่ Operator ใช้ระบุงานแรกที่ต้องทำ · **Guardrail:** การแจ้งเตือนที่พลาด

## 2. คิวตรวจถอนเงิน — Inbox + Approval (P01 + A03) · Critical

**งานหลัก:** ตัดสินใจคำขอถอนเงินให้ถูกต้องภายใน SLA 30 นาที

**การตัดสินใจสำคัญ**
- List–detail: ตัดสินใจเสร็จแล้วระบบเลือกรายการถัดไป ไม่ต้องเข้า–ออกหน้า
- Detail ตอบคำถาม "ควรอนุมัติไหม": ยอดและปลายทาง → หลักฐาน → ประวัติ → การตัดสินใจ
- ยอดเกินวงเงินของ Operator: ปุ่มอนุมัติถูกแทนด้วย "ส่งต่อให้ Manager" พร้อมเหตุผล
- ปฏิเสธต้องใส่เหตุผล; ก่อนบันทึกมี check answers ที่ระบุผลที่จะเกิด
  ([trust-security-privacy.md](../../references/trust-security-privacy.md), WCAG 3.3.4)
- บันทึกไม่สำเร็จ: บันทึกที่เขียนไว้ไม่หาย และรายการยังอยู่ในคิว

```text
Queue (เรียงจากรอนานสุด)          | WD-2048 · รอตรวจ · เสี่ยงกลาง · SLA bar
ค้นหา · [ทั้งหมด|เกิน SLA|เสี่ยง] | ฿125,000 → กสิกรไทย ****4821
แถว: ชื่อ, ยอด, ID, SLA, ความเสี่ยง | หลักฐาน: KYC, เหตุผลความเสี่ยง, ชื่อบัญชีตรงไหม…
                                    | ความเคลื่อนไหว (timeline)
                                    | บันทึก + [ปฏิเสธ…] [อนุมัติ…] (sticky)
```

**Metric:** % ตัดสินใจภายใน SLA · **Guardrail:** การตัดสินใจที่ต้องแก้กลับใน 7 วัน

## 3. ประวัติการทำรายการ — Audit log (A06) · Standard

**งานหลัก:** Auditor ไล่ย้อนว่าใครทำอะไร เมื่อไร เพราะอะไร

**การตัดสินใจสำคัญ**
- แถวเดียวต่อเหตุการณ์ (เวลา, ผู้ทำ + role, การกระทำ · เป้าหมาย); กดเพื่อดูค่าก่อน–หลังและเหตุผล
- ค้นหาด้วย ID ที่ผู้ใช้มีจริง; กรองตามการกระทำและผู้ทำ
- การตัดสินใจในคิวเพิ่มเหตุการณ์ที่นี่ทันที โดยใช้ชื่อสถานะเดียวกัน
- อ่านอย่างเดียว; การแก้ไขเป็นเหตุการณ์ใหม่

**Metric:** เวลาที่ใช้หาเหตุการณ์ที่ต้องการจาก ID · **ยังไม่ได้ทำ:** กรองช่วงวันที่, export

## 4. จัดการสิทธิ์ผู้ใช้ — Access management (A04) · Critical

**งานหลัก:** Manager เปลี่ยนสิทธิ์ผู้ใช้หนึ่งคนอย่างถูกต้อง เห็นผลก่อนบันทึก และตรวจย้อนหลังได้

**การตัดสินใจสำคัญ**
- แสดง **สิทธิ์ที่ใช้ได้จริง** พร้อมที่มา ไม่ใช่แค่ชื่อ role
- Focal point คือส่วนต่าง: ติ๊ก role แล้วตารางแสดง +เพิ่ม / −ถอด / ↕เปลี่ยนวงเงิน (สัญลักษณ์ + ข้อความ)
- Submission effect: เหตุผลบังคับ, กำหนดวันหมดอายุได้, ตรวจทานก่อนบันทึก
- Role ความเสี่ยงสูงต้องผ่านผู้อนุมัติคนที่สอง (maker–checker)
- บล็อกการรวม role ที่ขัดหลัก Separation of Duties พร้อมเหตุผล
- Operator ดูสิทธิ์ตัวเองได้แต่แก้ไม่ได้; ไม่มีใครแก้สิทธิ์ตัวเองได้
- Session ใกล้หมดอายุ: เตือนพร้อมนับถอยหลังและปุ่ม "ใช้งานต่อ" (WCAG 2.2.1);
  การแก้ไขที่ยังไม่บันทึกเก็บเป็นฉบับร่าง

```text
Identity header: ชื่อ · อีเมล · ทีม · เข้าใช้ล่าสุด · สถานะ · [แก้ไขสิทธิ์]
Role ที่ได้รับ (checkbox + ความเสี่ยง)  | สิทธิ์ที่ใช้งานได้จริง (ตารางตามหมวด + ที่มา + ส่วนต่าง)
เหตุผล · ระยะเวลา · [ตรวจทาน]            |
ตรวจทาน: เพิ่ม/ถอด, ผลที่จะเกิด          | ประวัติการเปลี่ยนสิทธิ์
```

**Metric:** % การเปลี่ยนสิทธิ์ที่ไม่ต้องแก้กลับใน 7 วัน · **Guardrail:** access incident

## สิ่งที่เรียนรู้ระหว่างสร้าง (จาก render check)

| ปัญหาที่พบ | สาเหตุ | แก้ |
|---|---|---|
| หน้าล้นแนวนอนบนมือถือ | Grid ไม่มี `minmax(0,1fr)` | กำหนด track ให้หดได้ |
| Stepper บิดเบี้ยว | Class `.done` ชนกับหน้า success | ตั้งชื่อ class ตาม component |
| Timeline ยืดห่าง | Grid stretch | `align-content:start` |
| Label กราฟซ้อนกัน | ตำแหน่ง label ไม่ได้กันชน | ย้าย label และเพิ่ม padding ใน viewBox |
| ข้อความไทยเป็น monospace | ใส่ฟอนต์ mono ทั้งบรรทัด | ใช้ mono เฉพาะ ID/ตัวเลข |
| ข้อความจางและขอบช่องกรอก contrast ไม่ผ่าน | เลือกสีด้วยตา | ตรวจด้วย `scripts/contrast.py` แล้วปรับ token |

ดูขั้นตอนเต็มใน [render-verification.md](../../references/render-verification.md)
